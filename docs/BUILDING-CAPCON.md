# Локальная сборка Capcon

На macOS и Linux запускайте команды из `src/`. Нужны Python 3.11+ и обычное
окружение Rust/FFmpeg. Скрипт использует `cargo` из PATH или переменной `CARGO`.

```sh
./dev build                         # собрать приложение
./dev run                           # собрать и запустить
./dev test -p concat-core --lib      # проверить затронутый модуль
./dev check -- -D warnings          # Clippy для приложения
./dev cache                         # показать объём кэша
./dev cache --trim                  # применить политику очистки
```

Все эти сборки используют `target/quick`, одинаковые настройки зависимостей
и оптимизированный движок. Обычная сборка сохраняет инкрементальный кэш UI.
Проверки и тесты отключают инкрементальный кэш только для большого UI-модуля:
они сохраняют скомпилированные зависимости, но не создают второй большой
вариант UI-кэша. Для быстрых итераций запускайте тесты нужного модуля; полный
набор и проверки CI остаются доступны.

Для `concat-speech` набор desktop-функций позволяет переиспользовать варианты
зависимостей приложения: `./dev test -p concat-speech --lib --features chatterbox,concat-host/gpu`.
Смена features всё ещё может потребовать другой вариант зависимости.

Политика в `src/.cargo/dev-cache.toml`:

- Бюджет инкрементального кэша — 8 GiB. При превышении удаляются самые старые
  варианты. Варианты без новых записей компилятора за 14 дней также очищаются.
- Последний рабочий кэш UI сохраняется, даже если он один превышает бюджет.
  При нехватке бюджета из него удаляются предыдущие завершённые снимки;
  последний завершённый снимок остаётся для следующей быстрой сборки.
  В таком случае скрипт явно сообщает об этом. Это бюджет после очистки,
  а не ограничение пикового размера во время работы компилятора.
- До сборки нужно 8 GiB свободного места. Если места меньше, скрипт завершится
  с понятным сообщением до запуска компилятора. Сначала он попробует вернуть
  этот резерв очисткой старых вариантов и предыдущих снимков кэша UI.
- Очистка работает только с каталогами компилятора в
  `src/target/quick/incremental` и захватывает тот же `.cargo-lock`, что Cargo.
  Если другая сборка уже идёт, очистка пропускается. Символические ссылки
  на каталоги кэша не обходятся.

Скомпилированные зависимости в `deps`, нативные библиотеки в `build`, готовые
приложения, проекты, медиа и сохранённые ответы API остаются на месте.
Старый `target/debug` эта политика также не очищает: он может содержать
установленный `.app` и его portable-данные.

Прямые команды `cargo dev`, `cargo dev-build`, `cargo dev-test`,
`cargo dev-check` используют те же настройки профиля, но обходят автоматическую
очистку. Для повседневной разработки используйте `./dev`. Release, CI и сборки
для iPhone/Android выполняются своими обычными командами Cargo.

При первом возвращении к инкрементальной сборке компилятор создаст рабочий
кэш заново. Проверять скорость следует по следующей сборке после небольшой
правки, а не по этому первому заполнению.
